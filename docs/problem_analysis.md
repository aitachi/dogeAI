# 🔴 API中介系统问题诊断报告

## 一、核心问题：并发控制设计缺陷

### 当前实现（错误）
```
时间线分析：用户A同时发送3个请求

┌─────────────────────────────────────────────────────────┐
│ 全局信号量（20个槽位）                                   │
├─────────────────────────────────────────────────────────┤
│ [T1] 占用槽位1 ✓ 获取用户锁 → 执行中                     │
│ [T2] 占用槽位2 ⏳ 等待用户锁... (浪费!)                  │
│ [T3] 占用槽位3 ⏳ 等待用户锁... (浪费!)                  │
│ [T4] 占用槽位4 ⏳ 等待用户锁... (浪费!)                  │
│ ...                                                     │
│ [T20] 占用槽位20 ⏳ 等待用户锁... (浪费!)               │
└─────────────────────────────────────────────────────────┘

问题：1个用户占用20个全局槽位，但只有1个在工作！
```

### 修复后（正确）
```
┌─────────────────────────────────────────────────────────┐
│ 用户级锁（先执行）                                       │
├─────────────────────────────────────────────────────────┤
│ 用户A: [T1执行中, T2排队, T3排队]                        │
└─────────────────────────────────────────────────────────┘
           ↓ 只有T1能获取信号量
┌─────────────────────────────────────────────────────────┐
│ 全局信号量（20个槽位）                                   │
├─────────────────────────────────────────────────────────┤
│ [槽位1] 用户A-T1 ✓ 执行中                               │
│ [槽位2] 用户B-T1 ✓ 执行中                               │
│ [槽位3] 用户C-T1 ✓ 执行中                               │
│ ...                                                     │
│ [槽位20] 用户T-T1 ✓ 执行中                              │
└─────────────────────────────────────────────────────────┘

效果：20个槽位可以被20个不同用户同时使用！
```

## 二、代码对比

### 修改前 (anthropic_proxy_v2.py:582-583)
```python
# 获取用户级锁（每个用户最多1个并发）
logger.info(f"等待用户锁: user_id={api_key_id}")
user_lock = await get_user_lock(api_key_id)

# ❌ 错误顺序：先占全局槽位，再等用户锁
async with semaphore:      # ← 先获取（20个槽位很快用完）
    async with user_lock:  # ← 再等待（造成槽位浪费）
        logger.info(f"获取用户锁成功: user_id={api_key_id}")
        active_requests += 1
        # ... 执行请求
```

### 修改后
```python
# 获取用户级锁（每个用户最多1个并发）
logger.info(f"等待用户锁: user_id={api_key_id}")
user_lock = await get_user_lock(api_key_id)

# ✅ 正确顺序：先等用户锁，再占全局槽位
async with user_lock:      # ← 先等待（不占用全局槽位）
    async with semaphore:  # ← 再获取（确保槽位高效利用）
        logger.info(f"获取用户锁成功: user_id={api_key_id}")
        active_requests += 1
        # ... 执行请求
```

## 四、上游API Key池管理

### 当前问题
```python
# anthropic_proxy_v2.py:279
CONFIG = {
    "UPSTREAM_API_KEY": "b8e22e2565834b0d9ce54dbb723fab34..."  # 单点故障!
}
```

**风险分析：**
- 🔴 所有用户共享1个上游key → 易触发限流
- 🔴 单key故障 → 全系统中断
- 🔴 无法分散负载和风险
- 🔴 无法按用户隔离配额

### 解决方案：多Key池架构

```
┌──────────────────────────────────────────────────────────┐
│                   用户请求层                              │
│  用户A(token1)  用户B(token2)  用户C(token3)              │
└────────────┬────────────┬────────────┬───────────────────┘
             │            │            │
             ▼            ▼            ▼
┌──────────────────────────────────────────────────────────┐
│              用户→上游Key绑定映射                          │
│  用户A → 上游Key-1  (固定绑定，防止任务中断)              │
│  用户B → 上游Key-2  (固定绑定，防止任务中断)              │
│  用户C → 上游Key-1  (负载均衡)                            │
└────────────┬────────────┬────────────┬───────────────────┘
             │            │            │
             ▼            ▼            ▼
┌──────────────────────────────────────────────────────────┐
│                 上游Key池                                 │
│  Key-1: active, 请求:45, 错误:0                          │
│  Key-2: active, 请求:38, 错误:0                          │
│  Key-3: error,   请求:12, 错误:3  ← 自动隔离             │
└────────────┬────────────┬────────────┬───────────────────┘
             │            │            │
             ▼            ▼            ▼
┌──────────────────────────────────────────────────────────┐
│                 上游API服务                               │
│         (智谱AI / Anthropic / OpenAI)                    │
└──────────────────────────────────────────────────────────┘
```

**优势：**
- ✅ 用户会话绑定：同一用户始终使用同一上游key
- ✅ 新用户分配新key：自动负载均衡
- ✅ 故障自动切换：错误key自动隔离
- ✅ 配额聚合：多key配额累加使用

## 五、防止任务中断机制

### 场景：管理员禁用用户token

#### 当前行为（硬中断）
```
1. 用户A正在执行请求T1 (耗时60秒)
2. 管理员禁用用户A的token
3. 请求T1完成后，用户A发起请求T2
4. T2被拒绝 → 任务链中断 ❌
```

#### 优雅禁用（软中断）
```
1. 用户A正在执行请求T1 (耗时60秒)
2. 管理员优雅禁用用户A的token
3. 系统检测到T1运行中，允许完成 ✓
4. T1完成后，用户A发起请求T2
5. T2被拒绝，但提示"token已禁用" ✓
6. 任务不会半途中断，用户可保存结果 ✓
```

**实现代码：**
```python
# 中间件检查
if not key_info.get('is_active'):
    disable_mode = key_info.get('disable_mode', 'immediate')

    if disable_mode == 'graceful':
        has_active = await _check_user_active_requests(key_info['id'])

        if has_active:
            # 允许完成，但记录日志
            logger.warning(f"Token已禁用，允许现有请求完成")
            return await call_next(request)

        return JSONResponse(status_code=403, content={
            "detail": "Token disabled",
            "mode": "graceful",
            "message": "Your token has been disabled. Please contact support."
        })
```
